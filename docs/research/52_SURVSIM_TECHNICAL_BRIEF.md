> **Terms used below (read once).**
> * **Alarm tolerance.** Unless stated, an alarm is a hit if it lands within
>   **30 s** after the event starts; later is a false alarm. The i-LIDS
>   protocol's own window is 10 s — reported alongside where it matters
>   (dwell rules cannot alarm before their own 25/60 s threshold, so at 10 s
>   they are almost un-scorable). **5 s** is not a tolerance: it is i-LIDS-style
>   *coalescing* of false alarms closer than 5 s into one (`ilids_compat`).
>   The CLI example `--threshold-s 25` is a rule threshold, not a tolerance.
> * **Window-only vs actor-aware recall.** Window-only credits any alarm of the
>   right label inside the tolerance window, even one raised on a bystander.
>   Actor-aware also requires the alarm's person id to be one of the event's
>   actors. Actor-aware is now the scorer default; every window-only number
>   is an upper bound.
> * **Positives for alarm recall.** Separate seeded "recall worlds" (300
>   worlds, ≈ 220 cam-h) with injected loiterers give **360 loiter events**.
>   The 3,002 clean cam-h (676 worlds) contain no loiterers and give only the
>   false-alarm rate.
> * **Precision** (alarm rules) = TP / (TP + FP) over alarms raised **in the
>   recall worlds** (tolerance 30 s, actor-aware where stated). It is not
>   computed on the clean hours, which have no positives.
> * **Label oracle.** A cheating "rule" that alarms at the true start of every
>   loiter episode: 0 FA by construction. Its recall is the scorer's ceiling
>   (1.000 actor-aware; 0.903 window-only, because two events starting within
>   30 s competed for one match).
> * **Kinematic-twin floor.** In the clean worlds, smoke breaks in gate zones
>   are generated by the *same motion process* as a loiter (`SmokeBreak`
>   subclasses `Loiter`: same 3 m pacing, same zones). No rule that sees only
>   tracks can separate them, so any such rule with recall r pays ≈ r × 1.008
>   FA/cam-h. It is a floor for *track-only* rules on these worlds — a property
>   of the task definition as generated, which context (zone function, time,
>   role) could break.
> * **Detection- vs association-limited** (tracking). A sequence is
>   detection-limited when HOTA's DetA < AssA (missed or false boxes cost more
>   than identity errors), association-limited otherwise.
> * **H11-B.** Part B of H11: fine-tuning on night renders, scored on real
>   MOT20-05.
>
> **Baselines — which 0.2x / 0.4x is which** (all yolov8n COCO weights, AP@640):
> **0.276** = zero-shot on MOT20-02 only (the set every trained arm is scored
> on, since trained arms saw MOT20-01); **0.281** = zero-shot on `mot20_sub`
> (MOT20-01 + 02, first 300 frames each), used only for arms with no real
> frames (H2, H16). **0.491 ± 0.003** = H1's real-only arm (60 MOT20-01 frames,
> 12 epochs, 3 seeds); **0.4862** = H14's real-only arm (same 60 frames, 6-epoch
> schedule, 5 seeds). Both real-only numbers are on MOT20-02.

## 1. What SurvSim is — and is not

**Is.** A multi-camera, multi-person surveillance simulator that produces
footage *plus the ground truth real CCTV can never give you*: who each person
is across cameras and across clothing changes, what they were doing and when,
whether a behaviour was actually observable from a given camera, and which
camera was tampered with. It exists to develop and, above all, **evaluate**
CCTV analytics — detection, tracking, cross-camera ReID, behaviour/intent,
degraded imagery, multi-sensor fusion — the way a security buyer evaluates
them: false alarms per camera-hour against an operator budget, and i-LIDS-style
timing where a late alarm counts as a false alarm.

**Is not.**
- Not a dataset. The product is the *scenario engine and the scoring*, not
  a pile of frames. Our own small synthetic set measurably *hurt* a real
  detector (H1, §4.4) — that is a finding, not a selling point.
- Not photoreal enough to replace real data. Realism scores 6/14 day, 3/14 [vs day targets; vs real LLVIP night 3/13 vis · 2/13 thermal, raw renders luma 90 = not dark (69 §7)]
  night against real-CCTV image statistics (§4.3).
- Not a trained model. Baselines are zero-shot YOLOv8n, ByteTrack, OSNet —
  instruments, not products.
- Not dependent on a live game engine for most of its value: the `mock`
  backend runs the whole behaviour → GT → eval loop in pure Python with no GPU.

## 2. Architecture

```
            scenario YAML (sites, cameras, people, behaviours, seed)
                                   |
                                   v
 +-----------------------------------------------------------------+
 | DIRECTOR (engine-agnostic, SI units, seeded RngHub per subsystem)|
 |  population gen -> planner -> behaviour engine (44 classes)      |
 |  appearance epochs (clothes change = new epoch, same identity)   |
 |  crowd model / avoidance     camera director (PTZ + 6 tampers)   |
 |  evasion taxonomy (52 techniques)   RF + audio sensor models     |
 +-----------------------------------------------------------------+
                  | per-tick actual agent state (after avoidance)
                  v
     +----------------------+          +-----------------------------+
     | BACKEND: mock        |    or    | BACKEND: unreal             |
     | top-down, no GPU, CI |          | editor/UnrealCV, SceneCap2D |
     +----------------------+          | masks -> boxes, bones       |
                  |                    +-----------------------------+
                  v                                   |
 +-----------------------------------------------------------------+
 | RECORDER  gt/writers.py: MOT txt, world.parquet, events.jsonl,  |
 |           identities.parquet, calib/, licences.json, COCO+kpts  |
 |           render gate (survsim/checks) blocks bad sets           |
 +-----------------------------------------------------------------+
                  v
 +-----------------------------------------------------------------+
 | DEGRADE  sensors/degrade.py: noise, auto-exposure, IR, codec    |
 |          (one ffmpeg GOP round-trip), profiles cctv_day/night    |
 +-----------------------------------------------------------------+
                  v
 +-----------------------------------------------------------------+
 | EVAL  alarms (FA/cam-h, i-LIDS timing), MOT (HOTA/IDF1),        |
 |       ReID across epochs, realism stats, rig coverage           |
 +-----------------------------------------------------------------+
```

Design rules that shape everything (CLAUDE.md "Non-negotiable principles"):
1. **Truth is what happened, not what was planned** — record post-avoidance
   state; boxes come from rendered instance masks, so they include occlusion.
2. **GT follows the live camera** — a slewed PTZ or a tampered camera no
   longer matches its configured pose; a blinded camera emits nothing.
3. **Hard negatives** — every suspicious behaviour is paired with an innocent
   look-alike (`commute_wait` vs `loiter`).
4. **Operational metrics** — FA/camera-hour vs a budget; late alarm = false alarm.
5. **One definition of visible** — `geometry.usably_visible` (in frame, in
   front, ≥ 20 px tall), shared by coverage analysis and event scoring.
6. **Determinism** — same seed ⇒ same run.
7. **SI above the backend** — the Unreal backend converts (×100, −Y, −yaw).

CLI surface: `survsim validate | run | rig | eval | experiment | audit-motion`,
plus `tools/render_batch.py` for engine renders.

## 4. What is measured

### 4.1 Rendering and throughput [V]

- **Headless editor renders work** — MRQ and SceneCapture2D under `xvfb-run`.
  The day-long "black render" was our bug: `unreal.Rotator(a, b, c)` is
  positionally (roll, pitch, yaw) in Python; a test now enforces keyword use.
  (`docs/BUG_black_render.md`, `97325e4`.)
- **Batch throughput:** 8 sets, 24 camera sequences × 300 frames = **7,200 frames in
  2,747 s (≈ 46 min)**, peak VRAM < 4 GB, on an 8 GB RTX 2070 Max-Q
  (`docs/12` §batch_v6, `7d1316a`); batch_v7 (CC0 cast) 7,200 frames in
  2,732 s (`docs/12` §batch_v7, `8c3b03b`); **batch_v8** 10,000 frames (9 sets) in
  10,664 s wall, editor VRAM peak 3.98 GB (`docs/12` §"batch_v8").
  **Why v8 is ~3× slower per frame (1.07 vs 0.38 s):** v8 renders a second,
  per-person **ID-mask pass** (`--id-mask`) for mask-derived boxes, then decodes
  it, builds amodal boxes and runs the new height and box-tightness gates per
  set. The decoder dominated: the old one took **4,168 s (≈ 70 min, measured)
  for the 4-camera disguise day set alone**, i.e. ~17 min per camera. The wall
  also includes two failed street_crowd_far attempts (96 s, 11 s) and a 1,478 s
  far re-run. The decoder was then rewritten: **33 s per 4-camera set,
  byte-identical MOT and parquet** (`1fd38df`), and a v8 set now takes
  370–900 s (`docs/12` §"batch_v8").
- **~11 fps render at 720p** is the planning figure used for sizing
  (`docs/research/23` l.155); the batch number above is the measured end-to-end
  (build + meter + render + gate) rate.
- **The packaged UnrealZoo runtime hangs at frame 1 [X]** — port open and
  handshake answered, no command executed (`docs/12` §2). Everything above
  goes through the UE 5.8.2 editor instead.

### 4.2 Data-quality gates [V]

- **Render gate** (`survsim/checks`, `scripts/check_render.py`, `dda3b98`):
  per-set checks — frame count, blank frames, GT-box motion (frozen fraction),
  exposure (luma 20–235, clip ≤ 0.25), horizon/sky, GT boxes in image, and
  more. The count scales with cameras (1 frame-count row + 9 per camera):
  **20 check rows** on the 2-camera sets, **29** on 3-camera, **38** on
  4-camera (counted in `out/batch_v7/*/check_render.txt`, 10 sets). A failing
  gate **blocks the encode**. batch_v6 and v7: 7/8 gated — the one failure
  in both is street_crowd_far night `cam_02:motion` (13–20 px people read as
  "frozen", 72.6 % / 71.6 %), documented (`docs/12` l.1081, l.1183).
  **batch_v8: 9/9 gate-clean** (far night now passes), with two new gates:
  `gt_height_matches_render` **PASS on all 9, 0 people beyond 2 cm** (v7 tightgt
  FAILed, up to 47.6 cm) and **box tightness** (median IoU vs detector
  **0.876–0.932**, gated on day sets) (`docs/12` §"batch_v8", `94145fa`).
- **Frustum gate** — no static within a camera's first metres (`f37d626`);
  **entrance gate** — each entrance framed *and* line-trace reachable.
- **Motion audit** (`survsim audit-motion`, `e5af8cd`): stuck fraction
  (> 3 s stationary under a walking label) **street_crowd 34.6 % → 0.0 %;
  disguise_and_tamper 49.1 % → 0.0 %**; t=0 overlap 100 % → 0 %. A regression
  test pins stuck < 2 %. (`docs/11` l.259–264.) Root causes: congestion at
  spawn and plan exhaustion — nobody noticed from videos because a slow crowd
  looks plausible.

### 4.5 Tight-GT box fix — committed (`0213002`, docs `68ee6d1`); label fit fixed, transfer not

H6 blamed loose box tops. New `survsim/gt/mask_boxes.py` +
`survsim/checks/box_tightness.py` derive boxes from instance masks instead of
projecting a body envelope, and score them against a detector:

| | n GT | median IoU vs detector | top offset (det − GT)/h | gate |
|---|---|---|---|---|
| before (projected) | 72 | **0.781** | +0.048 | top-offset **FAIL** |
| after (mask-tight) | 67 | **0.884** | −0.006 | PASS |

n GT differs because the gate uses the same 30 sampled frames but keeps
only GT boxes ≥ 40 px tall with visibility ≥ 0.7: mask boxes exclude occluded
and cut-off parts, so 5 of the 72 projected boxes fall below that bar (the
projected set also had 3 boxes with no detector match). Measured on `smoke_mock_day` (commit message of `0213002`: "0.781/+4.8 % →
0.884/−0.6 %"); files `out/batch_v7/smoke_mock_day_tightgt/box_tightness_before_projected.json`,
`.../box_tightness.json`. Gate: median IoU ≥ 0.75 and |top offset| ≤ 3 %.
`street_crowd_day`: 0.712 (FAIL) → **0.911**. Both tight sets now agree with the
detector *better* than MOT20-02's own hand labels do (0.797, `32` §H6(c)).
*Why a detector is the reference, and its limit:* the gate is not a
correctness test — the boxes are correct by construction (they are the extent
of the rendered mask). The detector checks the one thing that hurt transfer
in H6: whether our boxes sit where a person detector puts a person (loose
tops, offsets). Agreement with YOLO is therefore a *compatibility* gate, and
MOT20's 0.797 shows that correct human labels (amodal) can score lower on it.
Night sets are reported, not gated, because the detector misses dim people.

**Retrained — and it did not help** (docs/11 "Tight GT"): synthetic-only fine-tune on
the two sets (370 images, MOT20-02 @640, 2 seeds): loose **0.290 ± 0.024** vs tight
**0.266 ± 0.004** AP.
*Why loose 0.290 is above zero-shot 0.276 when H1's synthetic-only was 0.152:*
same detector, 12 epochs and eval set, but different training data. H1 used
**batch_v6** (MetaHuman cast), **5 scenes** incl. disguise day/night,
street_crowd night and far — 1,258 images, where the disguise labels carried
the ×1.5 scaling bug and night/far frames add hard, unlike-MOT20 content. The
tight study used **batch_v7** (CC0 cast), **2 day scenes** (smoke_mock,
street_crowd), all 1280×720 so no scaling bug, 370 images. Not a controlled
comparison; it says a small, clean, day-only pool does not hurt, and that
tightening its boxes does not help. Why: MOT20's boxes are *amodal* hand labels — the detector's
boxes are 13.5 % narrower than them (width ratio 0.865) — so "tight to the pixels" is
not "MOT20-like". Label fit was real but was not the transfer bottleneck. [V] negative.

**Amodal boxes — the third box type (`208cfc5`, docs/12 "Amodal boxes").** MOT20
labels the full body behind occluders; our mask box is the visible extent.
`survsim/gt/amodal.py` builds a full-extent box **without re-rendering**: a
calibrated projected body envelope (crown cylinder + torso ellipse + FK feet
at the rendered clip phase), corrected by per-person then local residuals
against clean mask boxes. Holdout on clean frames: IoU vs mask median
**0.921 / 0.907** (smoke / street; p10 0.791 / 0.765); on occluded rows the
mask lies inside the amodal box at median **0.988 / 0.979**. A per-box
**visibility fraction** is written too (street tightgt: median 0.996, **28 % of boxes
< 0.9**, 3 % < 0.5). These are the two v7 tightgt sets; the batch_v8 figures
(0.879–0.914, 12.5–19.4 % < 0.8) are §4.4. A second stencil pass cannot do this (CustomDepth is
depth-tested); a pass per person is exact but N× cost. H15 (amodal vs visible
→ real AP) is a path swap to `gt/amodal/mot_<cam>.txt`.
**Height gate now wired, and both tightgt sets FAIL it**: rendered before
`92e1e97`, every body is 1.70 m while GT says 1.22–1.89 m (worst +47.6 cm).
Boxes are unaffected (they measure the render), but `height_m` does not
describe those pixels. **Replaced by batch_v8** (every set PASS, 0 beyond 2 cm).

### 4.5b Render-height bug — fixed (`92e1e97`)

`build_manifest()` read `ident.get("wardrobe", ...)`, but `identities.parquet` has no

renders before `92e1e97` have a uniform 1.70 m body; the projected boxes' loose tops
(H6) partly came from this mismatch between Director height and rendered body
(`0213002` commit message).

## 5b. What synthetic buys (post-H26)

*The one sim-to-real story; 42, 46, 60, 64, 68, 77, 78, 79 and 80 mirror it. Numbers from FACTS_VERIFIED.*

1. **As a replacement for real data it hurts.** Synthetic-only fine-tuning lowers
   MOT20-02 AP from 0.276 to 0.152 ± 0.025 (H1, 3 seeds). At far range it collapses
   to AP50 0.000 in every seed on two render batches (zero-shot 0.613) until 60 real
   frames are added, which gives 0.817 (H19).
2. **As an add-on to real data the gain is small, and significant.** With
   optimiser steps held equal at 450 and 10 paired seeds (H51), 100 renders on top of 60 real
   frames give +0.0042 [+0.0024, +0.0062] and 300 give +0.0051 [+0.0037, +0.0064]
   over real-only 0.4911, Holm p 0.0039 both — about 1 % relative. H26 had found the same
   size at 5 seeds without clearing Holm; 600 gives +0.0015 and 1,000 gives
   −0.0003 (H26, not re-run). The h14b headline I used to quote is retracted (R51): it compared unequal
   steps, real-only alone gains +0.0049 from H26's longer recipe (steps, warm-up and mosaic all changed; AUDIT_H51), and at equal steps a third
   to a half of h14b's gain survives (AUDIT_H26: the split is not clean). H16's YOLO26n
   gain and H17's HOTA gain used the same unequal-step arms (R52, R53). H51 (10 seeds) settled
   it: "+0.004–0.005 AP at equal steps, Holm-significant, one site, one detector".
   H52/H61 (10 paired seeds each): the gain is labels on people — shuffled boxes erase it (+0.0077 gap), silhouette-masked frames with no box-shaped fill give nothing (−0.002 vs real-only); H52's apparent 'background' gain was the inpainted box fill. Duplicating real frames does nothing (−0.0011).
3. **What it reliably buys is not detector AP.**
   * *Ground truth real CCTV cannot give:* boxes from rendered masks, so occlusion is
     in the label (batch_v8 `94145fa`: gate 9/9, tightness IoU 0.876–0.932; recall 0.696
     vs v7 0.664 with the same characters, i.e. the gain was labels). Identities across
     outfit epochs, true calibration and act-time alarm scoring are built and used
     (principle 1 checked in AUDIT_H40B, `f45cf1b`), but they are capabilities, not a measured gain.
   * *Hard negatives on demand:* H40b's generated twins (`d51e5f9`) leave arm C at clean FA 0 but
     still cost patrol 0.389 and maintenance 0.099 FA/cam-h. That residual is only
     measurable because the twins could be generated. H53 (simulated gate log, RF tag, PIDS; matched on true
     positions) removes 99 % of it (0.488 → 0.0047 FA/cam-h) for 2.3 points of recall (0.782 → 0.758); a
     tailgater defeats it (AUDIT_H53) unless a gate people counter is added (0.685 recall, H54, with GT identities; H59: under H24-calibrated ID switches the actor-aware score for that fix drops to 0.10). Estimated-position
     matching keeps 99.1 % under a no-ID-switch noise model — an upper bound (AUDIT_H54); the alarm is credited to the

## 6. The honest gaps

1. **Sim-to-real is small** (full story §5b). Synthetic-only training hurts. As an add-on
   the gain is +0.004–0.005 AP at equal steps (H51, 10 paired seeds, Holm p 0.0039; the unequal-step h14b
   value is retracted, R51), on one real site, one detector and a 0.49 baseline. The value case rests on
   evaluation, coverage and ground truth, not on training data. Tight GT was
   re-run and did not help (0.290 → 0.266); more diverse bodies (heights now
   real since `92e1e97`) is the untested lever; amodal boxes were tested (H15, no effect, `b6c735e`). H13 gives a cheap screen: image-stat distance to MOT20
   ranks sources by transfer (ρ −0.60, n = 20, 1 seed).
2. **Realism** 6/14 day, 3/14 [vs day targets; vs real LLVIP night 3/13 vis · 2/13 thermal, raw renders luma 90 = not dark (69 §7)] night. Night IR in particular (H11: IR degrade
   blinds the detector) is not believable yet.
3. **Wardrobe and gait**: outfit epochs now render as palette swaps + a cap
   proxy (`99d986b`), not MetaHuman garments; H10 v2 has one changer and 3
   epoch-1 crops. Real gait extraction from MOT20 is downloaded, not written.
4. **Scale**: 8 GB GPU, ≤ 12 hero agents, 720p. Batches of 7,200 (v6/v7) to 10,000
   (v8) frames, not millions.
5. **Statistics**: H12 fixed the alarm side (3,002 camera-hours; Garwood CIs ±1–2 %, but
   the world-cluster CIs — the ones to quote, since alarms cluster by world —
   are ~3× wider, about ±4–5 %), but on *mock* trajectories with an
   unvalidated archetype mix. Elsewhere n is small (H10 v2 one changer; 10
   frames/camera for the CC0 comparison; H13 one seed). `docs/research/49` has the CI machinery; most rows need more data.
6. **No real deployment**: no RTSP/ONVIF hardware-in-the-loop yet (M3).

## 8. How to describe it

### 90 seconds
"SurvSim is a surveillance simulator I built to evaluate CCTV analytics
against ground truth real footage can't give you — identities across cameras
and clothing changes, exactly when a behaviour became visible, which camera
was tampered with. A Python director runs 44 behaviour classes with innocent
look-alikes for every suspicious one, drives either a pure-Python backend or
Unreal Engine 5.8, and writes MOT, parquet and event logs. It scores alarms
the way buyers do: false alarms per camera-hour against a budget, late alarms
count as false. The most useful results were negative: fine-tuning on our
renders cut real-world AP from 0.276 to 0.152; one cause was loose box tops,
mask-derived boxes lift median box IoU against a detector from 0.78 to
0.88 — tighter than MOT20's own labels — yet retraining on them did not help,
because MOT20's labels are amodal. Fixing the labels was right; it just was not
the bottleneck. The one positive: adding 100 renders to 60 real frames gives
+0.004–0.005 AP once training steps are held equal (H51, ten paired seeds, Holm-significant; the +0.012 we first reported compared unequal steps) — small, and one site. A learned
loiter rule beats a dwell timer 2× on false alarms (2.915 vs 6.0 FA/cam-h) at
2.2× the recall once alarms must land on the actual loiterer — and it is still
~2,900× over our assumed budget; zone context cuts another ~21 % but needs a site profile. I also found HOTA bugs that had
inflated our real-footage number to 0.545; the correct value is 0.434 (0.443 once matched exactly to TrackEval)."
